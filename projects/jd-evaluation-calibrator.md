# JD Evaluation Calibrator

### 模型不能改，也能从评估标准入手。

将模糊的职位描述转成明确的评估规则，帮助人工与 AI 使用更一致的招聘口径。

**方向：** LLM 评估、业务规则设计、人机反馈　·　**形态：** 宿主执行的 Skill v4.1.0

## 一个例子，看懂项目价值

| 原始表述 | 可能出现的误读 | 校准后的判断边界 |
| --- | --- | --- |
| “知识库项目经验优先” | 没有相关经验就否决 | 这是加分项，不能单独作为拒绝理由 |
| “掌握 Markdown、Notion 等工具” | 只认可列出的工具名称 | 其他工具完成同等任务，也可以作为能力证据 |

*以上为人工编写的说明性示例，不是模型实测结果，也不是完整规则库。*

在模型权重与系统提示词冻结、只能修改 JD 输入的场景中，业务团队仍可通过澄清要求、补充判断边界和样本回测，改善评估标准的执行方式。

## 如何工作

```mermaid
flowchart LR
    A[JD 与可选历史样本] --> B[分析判断分歧]
    B --> C[校准规则与边界]
    C --> D[人工细则与模型输入]
    D --> E[样本回测及人工确认]
    E --> C
```

| 模式 | 输入 | 交付物 |
| --- | --- | --- |
| 有样本标定 | JD、历史样本与人工判断 | 评估细则、证据矩阵、回测记录与模型输入文本 |
| 无样本改写 | JD | 歧义诊断、默认规则与待回测的输入文本 |

## 最后会交付什么

使用者提供 JD；如果有历史样本，也同时提供已经确认的人工判断。交付物围绕“标准是否清楚、模型是否照做”组织：

| 交付物 | 用来检查什么 |
| --- | --- |
| 修订后的 JD | 哪些表述存在歧义，哪些边界已明确 |
| 人工评估细则 | 不同经验档位如何判断，哪些要求是必要条件或加分项 |
| 岗位职责框与岗位要求框的文本 | 将标准填入既有评估工具的两个输入位置 |
| 样本证据矩阵与回测表（有样本模式） | 人工与模型在哪里产生分歧，修订后是否改善 |

交付后，将两段输入文本放入现有工具，用已确认且脱敏的样本重新评估，逐条核对分歧。仅有 JD 时会明确标记为“待回测”，不会把生成一份规则当成已经验证有效。

一个关键取舍是：人工细则保留权重，模型输入默认采用定性档位，让同一套业务要求分别适配人工审核和现有模型的输入方式。该流程依赖宿主提供模型与文件处理能力，没有独立 Web 服务。

## 我的贡献与实践记录

作为主要贡献者与评估流程设计者，我的工作包括误判分析、规则标定、Skill 封装、回测方法设计，以及后续 Error Case RAG 的架构与接口可行性评估。

| 记录 | 应如何理解 |
| --- | --- |
| **17 类误判模式** | 已整理的规则误执行类型，用于诊断与校准 |
| **2 种工作模式** | 有样本标定与无样本改写，分别处理不同材料条件 |
| **人机一致率 55% → 70%** | 特定业务场景的历史记录，增加 15 个百分点 |

一致率衡量人工与模型判断的吻合程度，不等于招聘质量或通用准确率。原始数据、样本量和完整配置未公开，这一历史结果尚不能独立复现，也不能据此确立因果效果。

## 当前进展与下一步

- **已实现：** Skill 工作流、配套规则与模板、有样本和无样本两条处理路径。
- **需要继续验证：** 独立留出集表现，以及规则经过下游解析或截断后是否保留。
- **架构方案：** 用错误案例检索支持下一轮校准的 Error Case RAG 尚未实现。现有接口缺少外部上下文注入能力，是后续集成需要解决的前提。

这个项目展示的核心能力是：在可修改范围有限的业务系统中，把隐含经验变成可执行、可回测的评估标准。
